# Frontend notes

Plain-language guide to the Cash Guard frontend, so anyone on the team can explain any part of it to the judges.
A new section is added after each build phase.

## Where the frontend lives

This repo holds one Replit app with two parts:

| Folder | What it is | Address |
|---|---|---|
| `artifacts/orbyte` | The website people see (our Cash Guard screens). | `/` |
| `artifacts/api-server` | The backend (T1): data, rules, calls to the AI on RunPod. | `/api` |

Both run on the same `.replit.app` link, so the website can reach the backend without any extra setup.

## How to update the live link

GitHub does not push to Replit by itself. After code is pushed to GitHub:

1. In Replit: **Tools → Git → Pull**. The preview restarts with the new code.
2. For the link the judges open: **Tools → Publishing → Publish**.

## The settings

Set in `artifacts/orbyte/.replit-artifact/artifact.toml` under `[services.env]`. They are public (they end up in the web page), never put keys there.

| Setting | What it does | If missing |
|---|---|---|
| `VITE_USE_MOCK` | `true`: use the built-in demo data. `false`: ask the real backend. | Demo data |
| `VITE_API_BASE_URL` | Backend address when demo data is off. Empty means "the same server" (`/api`). | Same server |
| `VITE_DEMO_MODE` | `true`: show the floating Demo button (bottom-right). | Button hidden |

## Changing the demo data (Google Sheet)

The demo reads its data from this Google Sheet:
https://docs.google.com/spreadsheets/d/1dkh9segLmkkAti3YY4dVHjWnJU2PVeS_HFPdFVBg9vk/edit

Change anything and the website picks it up by itself: it checks the sheet every 15 seconds and whenever you
switch back to its tab. Everything on screen follows: status, chart, what-if, actions, their wording and the AI explanation.
If someone has already approved or simulated something, the website does not wipe that demo by surprise:
it shows "Your Google Sheet has changed" with a "Load the new data" button instead.

Good to know: overdue invoices only count once a reminder is approved, so changing an overdue invoice
(amount or "Likely to pay %") changes the Actions and What if numbers, not the Overview headline.
Changing the bank balance, sales, payroll, bills or orders changes the headline straight away.

| Tab | What it holds |
|---|---|
| Settings | Company and people names, credits, demo date, check time, payday, buffer, bank balance, daily sales, payroll, staff count, which actions are allowed, and (optional) the AI explanation text. Column C explains each row. |
| Invoices | One row per customer invoice. Overdue = due date before "Demo today". "Message EN/BM" is optional; empty means a message is written from the data. |
| Bills | One row per bill. Fill "Can move to" only if the supplier allows a later date without penalty; that bill can then be suggested for moving. |
| Orders | One row per purchase order. Urgent = no and a "Can wait until" after payday makes it a "hold" suggestion. |

Rules: keep the column names in row 1; add or delete rows freely; rename tabs if you like, but do not delete and re-create a tab
(the website finds tabs by their fixed ID). The sheet must stay shared as "Anyone with the link can view".
If a cell is wrong (for example letters in "Amount"), the website shows the built-in data and a message such as
*"Invoices tab, row 3: "Amount" must be an amount like 2600 or RM 2,600.00"*. Fix the cell and press "Read the sheet again".

Under the hood: `src/mocks/sheet.ts` reads the 4 tabs as CSV, checks every value and builds a "scenario";
`src/mocks/engine.ts` runs on it; `src/mocks/aiText.ts` writes the sample AI wording from the numbers.
The sheet is chosen by `VITE_SHEET_ID` in `.replit-artifact/artifact.toml` (remove it to use the built-in data).
`src/mocks/sheetTemplate.ts` is the sheet's layout; a test proves it gives exactly the built-in numbers.

## Is the AI connected? (read this before the demo)

**Not yet.** With `VITE_USE_MOCK = "true"` the website runs on demo data. The AI explanation, the action ranking and the
EN/BM messages are sample texts written in advance (`artifacts/orbyte/src/mocks/fixtures.ts`). The screen says so:
a "Demo data" label in the top bar, "Sample AI text" under the explanation, "Sample draft" next to each message.

What is real today: SEA-LION on RunPod answers through `/api/ai-test` (page `/tes-ai`).

To connect Cash Guard to the real AI:

1. T1 builds the `/api/cash-guard/...` endpoints in `artifacts/api-server` (contract: `docs/frontend-api-contract.md`).
   The AI call can reuse the RunPod code in `artifacts/api-server/src/routes/ai-test.ts`. Numbers stay in normal code;
   the AI only writes the explanation, ranks the 3 action types and drafts the messages, with a rules-based fallback.
2. Set `VITE_USE_MOCK = "false"` in `artifacts/orbyte/.replit-artifact/artifact.toml`, Pull and Publish.
   The labels then switch to "Generated by SEA-LION · RunPod".

## Phase 1: Foundations

**What was built:** colours and fonts, and the rules for showing money and dates. No real screens yet: the page at `/` is a temporary check page. The AI test page (`/tes-ai`) still works.

| File (in `artifacts/orbyte`) | In plain words |
|---|---|
| `src/styles/tokens.css` | The design tokens: every Cash Guard colour, as a variable. |
| `tailwind.config.ts` | Turns the tokens into classes such as `bg-accent`, `text-title`, `rounded-card`. Tailwind's default colours stay available for the older pages. |
| `src/index.css` | Loads the tokens and Tailwind; sets the page background, text colour, Inter font and the focus ring keyboard users see. |
| `src/lib/format.ts` | Turns numbers into `RM 8,400.00` and dates into `25 Oct 2026`. Every screen uses it. |
| `src/lib/format.test.ts` | Automatic checks for `format.ts` (`pnpm --filter @workspace/orbyte run test`). |
| `src/lib/env.ts` | Reads the settings above, in one place. |
| `src/vite-env.d.ts` | Tells TypeScript the names of those settings, so a typo is caught. |
| `src/pages/scaffold-check.tsx` | Temporary check page. Replaced by the Orbyte shell in Phase 2. |
| `CLAUDE.md` | Standing rules for anyone (or any AI) writing code here. |

### Decisions worth knowing

- **We kept the repo's existing tools** (React 19, wouter, Tailwind 3) instead of the ones in the original frontend brief. Swapping them would risk breaking the working Replit setup.
- **The at-risk colour is `#985B00`, not the brief's `#B26B00`.** The brief's colour is too light for small text under WCAG AA (4.2:1, needs 4.5:1). The new one is 5.5:1.
- **Dates are built from a fixed month list**, because browsers now write September as "Sept". This also stops a viewer's time zone from shifting a date by a day.
- **Money uses a true minus sign**, as in the brief: `−RM 8,400.00`.
- **PO-077 fix (agreed with Owen):** in the brief, the RM 1,200 packaging order was never counted as money going out, yet "Hold purchase" claimed to save RM 1,200. From Phase 3 it counts as money out before payday, and the bank balance becomes RM 7,400 instead of RM 6,200, so every headline number in the brief stays the same (−8,400, +1,380, +2,580, +3,400).
- **No lint check yet:** adding a linter would change the shared install file used by the whole team.

## Phases 2–5: Orbyte shell, demo data, Overview, Actions

**What was built:** the clickable core of the demo. Open the site and it goes straight to Cash Guard inside a mock Orbyte workspace.
A judge can see the shortfall, understand why, try actions in "What if", open an action, edit the customer messages (EN/BM),
and approve it as Owner. The numbers update everywhere and the decision is recorded.

### How data flows

```
Screen (e.g. OverviewPage)
  → useApi(getSummary)                 src/lib/useApi.ts   loads data, shows loading/error, reloads after any change
  → client.ts                          src/api/client.ts   the only door to data
      mock mode → mocks/engine.ts      fake backend: the only place numbers are calculated
      real mode → fetch /api/...       T1's backend (same contract)
```

After any change (approve, reject, submit, run check), `client.ts` tells every screen to reload, so the Overview,
the sidebar status and the What-if panel all agree. In mock mode the demo is saved in the browser tab, so a page refresh keeps approvals.

### What each new file does (in `artifacts/orbyte/src`)

| File | In plain words |

| `api/errors.ts` | An error with a status code, e.g. 403 when a Finance Admin tries to approve. |

### Business rules (also in `docs/frontend-api-contract.md`)

- Invoices not yet overdue count in full. Overdue invoices count only once a reminder is approved, weighted by how likely the customer is to pay.
- Approving "Move bill" moves it to its allowed later date; approving "Hold purchase" moves the order to after payday.
- Safe if the balance after payroll is at least the buffer; At risk if between 0 and the buffer; Shortfall if below 0.
- Only the Owner approves, rejects or changes settings; only the Finance Admin submits for approval. Checked in the engine, not just by hiding buttons.
- Salaries are never touched: the AI can only pick from three action types.

## Switch to e-Salary Guard (24 Oct 2026)

The team changed the feature from Payroll Cash Guard to **e-Salary Guard**. `artifacts/orbyte` now holds a Next.js app
instead of the Vite Cash Guard app (Cash Guard stays in git history up to commit `5f962a0`; revert this commit to bring it back).

- **What it is:** `/` is a copy of the orbyte.my home page with one e-Salary Guard slot. Sign in at `/login` with a demo
  account (password `demo`): HR (`/hr/...`) sets the rules, approves leave and overtime, and pays the month in one click;
  employees (`/employee/...`) see their take-home pay, ask for leave or overtime, and get a WhatsApp-style message for
  every deduction. All data is fake and lives in the browser.
- **How the numbers flow:** every action goes through `lib/engine.ts`, which recalculates pay with `lib/payroll.ts`
  (only attendance deductions), writes the activity log, and creates a message when a deduction appears or changes.
- **Is the AI connected?** Yes. `app/ai/classify-leave/route.ts` sends the leave reason to SEA-LION on RunPod with the
  keys from Replit Secrets and returns "tolerated" or "deducted" with a one-line reason. HR always decides. If RunPod is
  slow (it sleeps when idle), the employee waits at most 8 seconds, then the keyword rules label it and the AI label
  replaces it when it arrives. Reasons that try to give the AI orders never reach it and go to HR review.
- **Why `/ai` and not `/api`:** on Replit every `/api` request goes to T1's Express server, so this route uses `/ai`.
- **`/tes-ai`** (T2's test page) was moved over unchanged; it still calls T1's `/api/ai-test`.
- **Checks:** 34 automatic tests (pay rules, actions, AI answer handling), typecheck and build. Clicked through the 8 demo
  scenarios from the spec in Chrome with the real AI.

## Revision: more flexible, payroll stays safe (24 Oct 2026)

Everything can be undone where it makes sense, but nothing in a paid month can change, and every undo or edit is in the activity log.

- **HR can undo a decision.** Approvals → "Decided and closed" → "Revert to pending" (with a confirmation). Pay is recalculated.
  Blocked with "This period has been paid" once the month is paid; overtime already marked done can't go back.
- **Salary & leave controls** (`/hr/salary`, was "Salary controls"): Global rules → Overtime rules and offers (moved here from
  the old Overtime offers page) → Pay per employee → Leave allowance per employee. Each employee now has a **division**
  (Café floor, Roastery, Logistics, Office); a division can have its own overtime rate (labelled Override) instead of the
  global one (labelled Default). The allowance is 14 days by default; only approved "Leave"-type days count as used.
- **Dashboard:** the "Employees with deductions" card has a "View deductions" link; the list below only shows people
  with a deduction, or "No deductions this period".
- **Attendance** (`/hr/attendance`, new): HR corrects a day (present / absent / izin, minutes late). The correction is stored
  next to the imported attendance (which is never changed), marked "Edited by HR", can be reset, and is logged with old → new.
- **"Today" is the real date (Malaysia time).** Attendance is "imported" only for days that have passed; future days are not
  counted as absent, so October pay is an estimate until the month is over.
- **Employees:** requests are saved instantly (the AI reads the leave reason in the background and HR sees its summary later).
  Pending: edit or withdraw (HR gets an update). Approved and not yet taken/worked: ask HR to cancel (shows up in HR's
  approvals as a cancellation request). Rejected: resubmit, prefilled. Withdrawn and cancelled requests stay in history.
- **Saved data:** browser data now has a version number. Older saved data is upgraded automatically (new fields added,
  nothing removed). Other tabs of the same browser update at once; other devices don't (there is no server).
- **Checks:** 47 automatic tests (13 new for these rules) and a browser click-through of all 8 items.

## Shared database (24 Oct 2026)

e-Salary Guard now keeps its data in **one shared Postgres database on Replit** instead of in each browser, so HR on a
laptop and an employee on a phone see the same requests and decisions within a few seconds.

- **Where the data is:** table `esalary_state` (declared in `lib/db/src/schema/esalary.ts`, added with T1's permission;
  Replit's post-merge `pnpm --filter db push` creates it). One row holds the whole demo state as JSON, with a version number.
- **Who may do what is checked on the server** (`artifacts/orbyte/lib/server/actions.ts`): HR-only actions, employees only
  on their own requests, input type-checked, signed sign-in cookie. Tested: an employee calling an HR action gets 403,
  a forged cookie 401.
- **Reset demo data** is HR-only now and asks for confirmation, because it resets the data for everyone.
- **Payslips:** the running month now shows as "not paid yet" and updates by itself; paid months stay frozen.
- **Without a database** (the laptop zip) the app works as before, each browser with its own copy.
- **Checks:** 57 automatic tests; in the browser, with a real Postgres: 8 demo scenarios, 8 revision items, and a
  two-device test (a request from one device shows up on the other in about 2 seconds, a decision in under a second).
- **Payment history (HR)** now also shows the running month for every employee as "Not paid yet · estimate", updating
  live; once HR pays, it becomes the frozen paid snapshot. The employee's Payslips page uses the same view.

## Demo spaces, "Try it live", phone layout (24 Oct 2026)

- **Demo spaces:** each visitor (each judge) automatically works in their own copy of the demo data, so nobody can break
  the demo for the next person. To use two devices together, open the link shown on the sign-in page
  (`/login?space=CODE`) on the second device. Reset only resets your own space.
- **Try it live** (HR dashboard): choose an employee and click "25 min late" or "Didn't come in"; the WhatsApp alert and
  the new take-home pay appear immediately, with an Undo button. It uses the last working day that has passed.
- **Phones:** a bottom tab bar replaces the sideways-scrolling menu (HR: Home, Rules, Approvals, Payroll, More), every
  table turns into cards, forms put paired fields side by side, and buttons/fields are at least 44px tall.
- **Checks:** 61 automatic tests; browser tests in both modes (demo 22, revision 23, two-device + separate-space 9,
  slow AI 4), and a phone audit: no page or table scrolls sideways any more.

## Easier to understand: plain words, clear starting points (24 Oct 2026)

- **One word list** (`lib/words.ts`) used on every screen: "Paid leave" / "Unpaid leave" (was Tolerated / Deducted),
  "AI suggestion" / "Keyword check" / "Set by HR" (was AI / Fallback / HR), "Please check" (was Needs review),
  "Permitted absence" (was izin), "Own rate" / "Same as everyone" (was Override / Default), "Undo decision" (was Revert).
  Each leave shows one main badge and at most one small note.
- **HR dashboard** starts with "What needs you now": real tasks, each with one button (decide requests, review payroll,
  see who had a pay cut). The numbers moved below it.
- **Employee "My salary"** starts with one sentence: how much, why less (with dates), and whether anything needs doing.
- **Sign-in page** has a "Try it in 3 steps" card (can be hidden; remembered in this browser only). Every page now opens
  with one sentence saying what the page is for.
- **Pay & leave rules** is split into tabs (Rules · Overtime · Pay · Leave allowance). The address follows the tab, so
  `/hr/salary#overtime` and the old `/hr/offers` link open the Overtime tab.
- **Approvals** is one "To decide" list (leave, overtime and cancellation requests) with an All / Leave / Overtime filter,
  and a History panel below.
- Secondary buttons look like buttons; success and error messages use one component (`Notice`) right under the action;
  empty lists say what to do next. On phones the "Pay everyone" bar stays visible while scrolling the payroll.
